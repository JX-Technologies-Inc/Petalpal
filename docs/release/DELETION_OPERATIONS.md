# Deletion operations and publication checklist

Local code only. No production execution authorized.

- Owner confirms delivery/access coverage for contact@jastrevia.com and the legal publisher. The deletion page is published from `mobile/public/legal/account-deletion.html` at https://app.jastrevia.com/legal/account-deletion.html (2026-10-22, see [LEGAL_PUBLICATION.md](LEGAL_PUBLICATION.md)). No new URL is claimed here.
- Test opening the public resource on an uninstalled-device browser, sending from a disposable account mailbox, receiving and processing it, and receiving completion. Add the exact tested URL in Play Console. A mailto action opens a draft, not a submission confirmation.
- Staff verify control of the registered mailbox using an approved challenge. Never request passwords/tokens/private entries. For lost-mailbox cases, use an owner-approved recovery process; do not delete on an unverified claim.
- Approved operator executes the same `requestAccountDeletion` service with the verified server-resolved user/UID pair. Never accept raw caller-supplied ownership as proof. Use least-privilege server tooling, record minimal audit outcome and notify the requester. No public unauthenticated deletion API is prepared.
- Database erasure and AccountDeletion retry record commit together. Firebase deletion follows. A Firebase or completion-record failure returns pending, retains the retry record and cannot recreate content. `scripts/resume-account-deletions.js --execute-authorized` retries up to 100 pending identity deletions, emits counts only, and is idempotent. Operator must run/reconcile this on each staffed day and before telling a requester that deletion is complete. Automation/deployment requires separate approval.
- Pending records contain only user ID, Firebase UID and timestamps; retain until reconciled. Completed tombstones currently have no automatic expiry; owner must approve a retention schedule and purge process. Do not invent a finite guarantee in published policy. Non-cascading AuditEvent cost reservations also remain to prevent duplicate spend/replay; establish a justified retention limit before launch.
- Restore procedures must reapply completed deletion records before exposing restored backups; otherwise old private data could reappear. Provider-specific deletion requests, backups, logs and mailbox retention require owner/provider action. Database cascades cannot erase those copies.
- Existing deletion unit evidence that rolled back PostgreSQL on a Firebase failure is superseded by the durable erasure/retry contract. Preserve that historical record; real PostgreSQL tests now verify erasure, rollback on database failure, idempotent identity retry, vectors, unrelated owners and resurrection denial.
